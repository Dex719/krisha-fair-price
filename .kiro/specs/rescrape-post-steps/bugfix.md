# Bugfix Spec: шаг Alerts душит заливку базы в ночном rescrape

- **Slug:** `rescrape-post-steps`
- **Тип:** Bugfix Spec, проведён как Quick Spec (один проход без промежуточных гейтов:
  план согласован владельцем 2026-09-23 — «пофикси баги» после разбора)
- **Заведено:** 2026-09-23
- **Симптом:** прод-смоук красный `freshness='stale'` (2026-09-20 18:12 и 2026-09-21
  08:56, `data_age_hours` 31.75 и 46.5); прод двое суток отвечал на данных 19.09.

## 1. Current behavior (как есть)

Порядок шагов джобы `rescrape` в [rescrape.yml](../../../.github/workflows/rescrape.yml):

```
Rescrape (мягкий бюджет 320 мин) → Job summary → Alerts (continue-on-error, БЕЗ timeout)
  → Upload DB to release → Restart Space → Snapshot release
```

Потолок всей джобы — `timeout-minutes: 350`. Шаг `Alerts` запускает
[send_alerts.py](../../../scripts/send_alerts.py), а тот — `find_good_deals()`
([alerts.py:87](../../../src/krisha/alerts.py)): для КАЖДОГО лота окна 26 ч
(`first_seen` или `scraped_at`) вызывается полный `predict_from_listing` —
CatBoost + SHAP + подсказки к факторам + история цены/ликвидность/скам + аналоги
(kNN) + `log_prediction`, причём без переданного соединения: своё `get_conn` и
коммит на каждый лот. Стоимость ~0.5–0.75 с на лот, строго линейно.

Фикс `safeline-468` (влит 2026-09-17) оживил краулер: вместо 0 докачанных деталей
(17.09, 3498 × HTTP 468) — 2.3–3.4 тыс. деталей и ~650 устаревших за проход. Окно
алертов выросло до 4–7 тыс. лотов, шаг — до часа с лишним:

| Дата | Rescrape | Alerts | Предиктов в `predictions` | Итог |
|---|---|---|---|---|
| 09–17.09 | 1ч47–5ч20 | 0–19 мин | ≤ 2.7 тыс. | ok |
| 18.09 | 4ч55 | 41 мин | 4104 | ok |
| 19.09 | 4ч48 | 56 мин | 6784 | ok |
| **20.09** | 4ч43 | **>71 мин** | — | **джоба убита по 350 мин** |
| 21.09 | 4ч42 | 47 мин | 3839 | ok |
| 22.09 | 4ч11 | 80 мин | 6482 | ok, запас ~18 мин |
| 23.09 | 4ч16 | 72 мин | 5795 | ok, запас ~20 мин |

2026-09-20: `Rescrape` 05:57→10:40 успешно, `Alerts` 10:40→(убит в 11:51);
`Upload DB`, `Restart Space`, `Snapshot` не выполнены. 4 ч 43 мин сбора потеряны,
прод остался на данных 19.09 — два красных смоука `stale`.

Что делает результат `find_good_deals`: подписчиков на выгодные лоты нет (лог:
«Подписчиков на выгодные лоты нет»), результат уходит в пост «Топ-5 лотов дня»
в канал и в таблицу `predictions` (issue #128) — +~6 тыс. строк в день.

**Смежный дефект того же конвейера — снапшот-релиз.** 2026-09-13
`publish_snapshot.py` получил HTTP 500 от GitHub на `gh release create`; `gh`
оставил релиз `snapshot-2026-09-13` черновиком. Вечерний rent-воркфлоу нашёл
«существующий» релиз и дописал в черновик свою базу. Итог: снапшота продаж за
13.09 нет, rent-база спрятана в неопубликованном черновике. Ретраев нет.

## 2. Expected behavior (как должно быть)

- **FR-1 (Must).** WHEN шаг `Rescrape` завершился, THEN workflow SHALL залить базу
  в релиз, рестартовать Space и опубликовать снапшот ДО любого вторичного шага.
- **FR-2 (Must).** Шаг `Alerts` SHALL иметь собственный `timeout-minutes`, чтобы
  не мог съесть бюджет джобы.
- **FR-3 (Must).** WHEN `find_good_deals` оценивает окно, THEN он SHALL делать это
  пакетно: признаки и оба CatBoost-предикта — одним вызовом на порцию лотов, только
  то, что нужно алертам (`fair_price`, интервал, `verdict`, `diff_pct`), без SHAP,
  подсказок, рынка и аналогов.
- **FR-4 (Must).** Пакетная оценка SHALL давать те же `fair_price`,
  `fair_price_low/high`, `verdict`, `diff_pct`, что `predict_from_listing` для
  того же лота: формула цены/интервала/вердикта — в одном месте кода.
- **FR-5 (Must).** Предикты окна SHALL записываться в `predictions` одной транзакцией
  с теми же полями, что пишет `log_prediction` (долговечный JSON-лог не трогаем —
  в Actions он выключен по построению).
- **FR-6 (Should).** WHEN `Alerts` завершился успешно, THEN workflow SHALL залить
  базу повторно, чтобы предикты алертов попали в `db-latest`. IF `Alerts` упал или
  вышел по таймауту, THEN в релизе остаётся база из FR-1 — собранное не теряется.
- **FR-7 (Should).** WHEN публикация снапшота падает на временной ошибке, THEN
  `publish_snapshot.py` SHALL повторить её (до 3 попыток с паузой) идемпотентно и
  SHALL оставить релиз опубликованным, а не черновиком — в том числе релиз,
  который черновиком оставил прошлый сбой.
- **NFR-1.** Шаг `Alerts` на окне ~6 тыс. лотов — не дольше 5 минут (замер на
  реальной базе и модели).
- **NFR-2.** Бюджет джобы с запасом: Rescrape ≤ 320 + заливка/рестарт/снапшот ~3 +
  Alerts ≤ 15 + повторная заливка ~2 ≤ 340 < 350 мин.

### AC (Given/When/Then)

- **AC-1.1.** Given `rescrape.yml`; Then шаги `Upload DB to release`, `Restart Space`
  и `Snapshot release` стоят раньше `Alerts`, а у `Alerts` задан `timeout-minutes`
  (проверяется тестом по YAML).
- **AC-3.1.** Given N лотов окна; When `find_good_deals`; Then `predict_from_listing`
  не вызывается ни разу, CatBoost-модель вызывается по разу на порцию.
- **AC-4.1.** Given реальная модель из `models/` и набор разнородных лотов (с ценой,
  без цены, без координат, новостройка/вторичка); When пакет против поштучного
  `predict_from_listing`; Then `fair_price`, `fair_price_low`, `fair_price_high`,
  `verdict`, `diff_pct` совпадают для каждого лота.
- **AC-5.1.** Given окно из N лотов; Then в `predictions` появляется ровно N строк
  с теми же значениями, что вернул пакет.
- **AC-7.1.** Given `gh release create` падает с HTTP 500 один раз; When
  `publish_snapshot`; Then вторая попытка доводит релиз до опубликованного, заметки
  не дублируются.
- **AC-7.2.** Given релиз-черновик с этим тегом уже существует; When `publish`;
  Then ассеты дописаны и релиз опубликован (`--draft=false`).

## 3. Unchanged behavior (что не трогаем)

- Состав окна (`new_listings`), фильтры подписок, форматы сообщений, дедуп
  `alerted_ids.json` / `channel_posted.json`.
- Пост «Топ-5»: те же лоты в том же порядке (сортировка по `diff_pct`).
- Пользовательская карточка `predict_from_listing` — результат без изменений.
- Сам шаг `Rescrape`, его параметры и бюджет; rent-воркфлоу (там шага Alerts нет).
- Долговечный лог `prediction_log` (JSON): в Actions выключен, пакет его не пишет.
- Ротация снапшотов и формат заметок релиза.

## 4. Root cause (первопричина)

Вторичный шаг стоит на критическом пути. Заливка базы — единственное, ради чего
джоба существует, — ждёт шаг, чья стоимость по построению O(N × полный
пользовательский предикт) и у которого нет своего потолка. Пока краулер из-за
SafeLine почти ничего не докачивал, N было мало и связь не проявлялась; фикс
`safeline-468` поднял N в разы — и скрытая зависимость сработала.

## 5. Регрессии — что проверить после фикса

- `pytest` весь набор — без новых красных (известное красное локальной среды:
  `test_static_precompress` на Python 3.14 + starlette 1.3, в CI на 3.11 зелёный).
- Эквивалентность пакет/поштучно на реальной модели (AC-4.1).
- Замер `find_good_deals` на свежей базе прода (NFR-1).
- Первый ночной rescrape после мержа: `Upload DB` раньше `Alerts`, `Alerts` ≤ 5 мин,
  утренний смоук — `freshness: ok`.
