# Roadmap: от «честной цены» к рейтингу квартиры 0–100

Цель — превратить сервис из калькулятора цены в полноценного «помощника покупателя»:
один общий скор квартиры **0–100** + понятная разбивка, почему именно столько.

Пример карточки, к которой идём:

```
Квартира: 78/100
✅ Цена ниже рынка на 8%
✅ Свежий ремонт, средний этаж
⚠️ Шумная дорога в 50 м
⚠️ В описании упомянут залог
```

Скор собирается из пяти блоков: **квартира, дом/ЖК, локация, сделка, описание/фото**.
После каждого этапа — переобучение модели и честное сравнение MAE/MAPE:
оставляем только то, что реально улучшает качество.

---

## Этап 1. Неиспользуемые поля объявлений + переобучение (quick win)

Данные уже лежат в базе (`raw_params`), но модель их не видит:

- **Состояние ремонта** — заполнено у ~60% объявлений:
  `свежий ремонт`, `не новый, но аккуратный`, `черновая отделка`, `требует ремонта`.
  Разница «черновая vs свежий ремонт» — это легко 15–25% цены.
- Санузел (раздельный/совмещённый/несколько)
- Мебель (полностью/частично/без мебели)
- Парковка (паркинг/гараж/во дворе)
- Безопасность (охрана, домофон, видеонаблюдение)

Задачи:

1. Распарсить эти поля из `raw_params` в нормальные фичи (+ категория «не указано»).
2. Переобучить CatBoost, сравнить MAE/MAPE/R² с текущим бейзлайном
   (MAE 7.65 млн ₸, MAPE 10.6%, R² 0.78).
3. Обновить `models/stats.json` и форму оценки на сайте (новые необязательные поля).

**Бонус — бейдж сделки:** цена объявления vs прогноз модели уже считается,
осталось подать как бейдж «ниже рынка на 8%» / «выше рынка на 12%» на странице оценки.

## Этап 2. Дом и ЖК: застройщик, класс жилья, год сдачи

В объявлениях этих данных нет, но на krisha есть каталог ЖК со страницами комплексов.

1. Разово спарсить каталог ЖК Алматы (несколько сотен страниц): застройщик,
   класс жилья (эконом/комфорт/бизнес/премиум), год сдачи, материал, этажность.
2. Сохранить в отдельную таблицу `complexes`, джойнить по `complex_name`
   (нормализация названий: регистр, кавычки, «ЖК»-префиксы).
3. Добавить фичи в модель + показывать блок «О доме» на странице оценки.

Этаж/этажность/первый-последний этаж уже в модели — здесь ничего делать не надо.

## Этап 3. Локация: walkability-скор по OpenStreetMap

Координаты каждого объявления уже есть. Через OSM (Overpass API) считаем:

- расстояния до метро, школ, детсадов, парков, супермаркетов;
- свой walkability-скор по радиусам (500 м / 1 км);
- **анти-факторы**: крупная трасса под окнами, промзона рядом.

Это частично закрывает вопрос «где стоит дом внутри района/ЖК»:
точных данных «этот блок у дороги, тот у двора» нигде нет,
но расстояние до магистрали по координатам — хорошая замена.

## Этап 4. История цены и ликвидность (регулярный рескрейп)

Скрейпер уже умеет ходить по 8 районам без банов (задержки 0.8–1.6 с).
Запускаем его по расписанию и начинаем копить историю:

- **История цены объявления** — видно, кто снижал цену
  (сигнал, что торг реален) → график на странице объявления.
- **Дни на рынке / ликвидность** — сколько висят похожие квартиры
  до исчезновения с сайта → «такие уходят за ~2 недели».

## Этап 5. LLM-анализ текста описания

Поле описания сейчас не используется. LLM-проход по тексту даёт:

- **Red flags:** «срочно», «в залоге», «ипотека», «без торга», «по доверенности».
- **Плюсы, которых нет в полях:** «окна во двор», «тёплая», «новая сантехника»,
  «развитая инфраструктура».

Результат — список бейджей ✅/⚠️ в карточке оценки. Гонять только на новых
объявлениях, кэшировать в базе.

## Этап 6. Оценка ремонта по фото (vision-LLM)

Самый эффектный пункт, но и самый дорогой: vision-модель смотрит фотографии
и ставит оценку ремонту/свету/кухне по шкале 1–5.

- 7000+ объявлений × LLM-вызов = медленно и упираемся в лимиты бесплатных ключей,
  поэтому этап последний.
- Запускать только на новых объявлениях и/или по запросу пользователя
  на странице конкретной квартиры.
- Дополнительно: сверять оценку по фото с заявленным «состоянием» из этапа 1
  (расхождение — само по себе red flag).
