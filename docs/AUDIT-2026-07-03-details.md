## 4. Детали по фазам

### 4.1 Качество кода

Структура пакета чистая: `scraping/` (клиент, парсеры, краулер), `api/` (app + pydantic-схемы), плоские доменные модули (`features`, `train`, `predict`, `market`, `bot`, ...). Разделение ответственности выдержано; циклических импортов избегают осознанно (ленивые импорты внутри функций с комментариями). Наименования последовательные и говорящие. Типизация: ~88% функций с аннотациями возврата (209 из 238), современный синтаксис `X | None`. `[data: 2025]`

Обработка ошибок — сильная сторона: 24 `except Exception` — все с логированием и комментарием-обоснованием (`# noqa: BLE001 — аналоги не должны ломать оценку`), паттерн «fail-soft с журналированием» выдержан. Голых `except: pass` нет. Из минусов: широкие перехваты `sqlite3.OperationalError` c возвратом пустых значений (`db.py`, `llm_flags.py`) могут маскировать реальные проблемы схемы, не только read-only ФС; сообщение `RuntimeError` уходит пользователю бота как есть (`bot.py:302`) — сейчас тексты безопасны, но канал для утечки внутренних деталей открыт. Мёртвого кода и древних TODO не обнаружено; docstring-и есть у всех модулей. Ruff сконфигурирован (E, F, I, W), но без правил безопасности/сложности (`B`, `S`, `C90` не включены). `[data: 2025]`

### 4.2 Архитектура

Монолит FastAPI обслуживает сайт (статичный vanilla JS), REST API и Telegram-webhook; батч-работа (краулинг, рескрейп, обучение, рассылки) вынесена в GitHub Actions — для одного оператора и текущего масштаба это разумно. Внешние интеграции: krisha.kz (скрейпинг), Gemini API (LLM-флаги, vision, парс текста), Telegram Bot API, GitHub API (персистентность состояния).

Ключевая архитектурная ставка — «бесплатная инфраструктура как база данных»: SQLite скачивается из GitHub Release при старте, JSON-состояние (подписки, слежка, usage) коммитится в git через Contents API, потому что диск Space эфемерен. Это креативно и честно задокументировано, но несёт системные следствия: (а) всё состояние процесса — одноэкземплярное (rate limit, дедуп update_id, кэши — в памяти процесса; горизонтальное масштабирование невозможно без переделки); (б) read-modify-write подписок через GitHub API не атомарен — параллельные изменения от двух пользователей могут потерять одно из них (сейчас вероятность мала); (в) серверные записи в SQLite живут до ближайшего рестарта (находка #4). Единая точка отказа — GitHub: релизы, состояние, деплой, расписания. `[data: 2025]`

Связность модулей контролируемая: `db.py` не знает про FastAPI, парсеры не знают про модель, бот переиспользует `predict_from_url`. Заметное исключение — `features.py` импортирует `FLAGS_RU` из `llm_flags.py` на уровне модуля (ML-слой зависит от LLM-слоя), а комментарий в `predict.py` («LLM-флаги — теперь и фичи модели») противоречит факту, что `FLAG_FEATURES` выключены абляцией — мелкий дрейф комментария и кода.

### 4.3 База данных

SQLite + сырой SQL без ORM — адекватно объёму (~44 тыс. объявлений). Схема продумана: `listings` с временными полями жизненного цикла (first_seen/last_seen/is_active/delisted_at), `price_history` с составным PK, `complexes`, кэш-таблицы `llm_flags`/`vision_renovation`. Индексы под реальные запросы: district, rooms, fingerprint (с комментарием, зачем), price_history(listing_id). WAL + busy_timeout=5000 включены с объяснением. UPSERT грамотный: `excluded.*` для «источник истины — свежий парс», COALESCE для защиты хороших данных от неполного парса. `[data: 2025]`

Миграции — самодельные идемпотентные (`_migrate`: PRAGMA table_info → ALTER TABLE ADD COLUMN + бэкфилл). Для одной таблицы работает, но версионирования схемы нет: порядок применения и история изменений живут только в коде, откат невозможен. Транзакционность: `get_conn` коммитит по выходу из контекста — многошаговые записи внутри одного контекста атомарны, ок. NOT NULL/constraints почти не используются (почти все колонки nullable) — компромисс под грязные данные скрейпинга, осознанный. N+1: находка #10 (LLM-фичи при обучении); в рантайме предикта запросы точечные по PK — нормально. Пагинации на выдаче нет, но и list-эндпоинтов, отдающих таблицы целиком, нет. Бэкап: продажная база — ежедневный gzip в GitHub Release (это и есть бэкап с глубиной в один снимок, `--clobber` затирает предыдущий — истории нет); rent-база — так же; серверные приросты — не бэкапятся (находка #4).

### 4.4 API

Дизайн консистентный: `/api/predict|stats|flags|heatmap|forecast|health`, snake_case, вменяемые коды (422 валидация, 429 лимит, 502/503 с обобщёнными текстами). Pydantic-схемы полные, с комментариями на каждое поле — OpenAPI получается содержательным. Версионирования (`/v1/`) нет — для публичного API с Mini App-клиентом пока приемлемо, но контракт с фронтом ничем не зафиксирован, кроме самих схем. `[data: 2025]`

Валидация входа: `PredictRequest.url` — свободная строка, канонизируется регэкспом (SSRF закрыт), но без ограничения длины (находка #11). Auth: публичных мутирующих эндпоинтов нет; webhook защищён секретом. Rate limit — скользящее окно на IP в памяти с потолком ключей (находка #7 про XFF). CORS не сконфигурирован — значит, действует same-origin по умолчанию, что здесь правильно. Таймауты исходящих вызовов заданы; таймаута на сам request-обработчик нет (усугубляет находку #2). Кэши `/api/stats|heatmap|forecast` — TTL 10 мин в module-level dict: не потокобезопасно, но худший случай — параллельный пересчёт, приемлемо.

### 4.5 Безопасность

Крепкая для пет-проекта. Закрыто: SSRF (канонизация URL), XSS (экранирование на бэке `html.escape` и фронте `esc()`/`safePhoto()` + CSP), SQL-инъекции (всюду параметризация; единственные конкатенации — DDL с захардкоженными именами колонок и статичными WHERE-литералами — безопасно), webhook-подделка (секрет из SHA-256 токена + `compare_digest`), секреты в коде (нет, проверено), prompt-injection в Gemini (выход зажат responseSchema + серверный whitelist ключей флагов — инъекция максимум расставит неверные бейджи). Dockerfile: непривилегированный пользователь, slim-образ. `[data: 2025]`

Открытые вопросы — по таблице: PII в публичном git (#1, главное), PAT в рантайме (#5), DoS через медленные ретраи (#2) и XFF (#7), целостность скачиваемой базы (#16), потенциальный токен в логах (#19). Отдельно отмечу юридическую плоскость: скрейпинг krisha.kz идёт вежливо и с дисклеймером, но пользовательское соглашение площадки в репозитории не анализируется — стоит понимать этот риск. `[data: unknown — verify]`

### 4.6 Зависимости

Мёртвых зависимостей нет: все 14 объявленных пакетов реально используются (lxml — как parser-бэкенд BeautifulSoup, uvicorn — сервер в Dockerfile/Makefile). Дублирующих друг друга библиотек нет. Все версии — плавающие `>=` без верхних границ и без lock-файла (находка #3). Сводно: подбор зависимостей дисциплинированный, «зоопарка» нет. Отдельное наблюдение: train-только зависимости (shap, matplotlib, scikit-learn, scipy частично) устанавливаются в прод-образ, раздувая его на сотни МБ — extras-группы вида `[train]` в pyproject нет. `[data: 2025]` Внешний API-контракт с Gemini захардкожен на `gemini-2.5-flash-lite` — доступность и лимиты модели требуют внешней проверки `[data: unknown — verify]`. (Полная таблица оценок по каждой зависимости — в оригинале отчёта; сокращена при переносе.)

### 4.7 Деплой и CI/CD

**Dockerfile:** компактный и правильный для HF Spaces (порт 7860, non-root uid 1000, `--no-cache-dir`, editable-install с объяснением зачем). Минусы: базовый образ `python:3.11-slim` не пиннится ни тегом минорной версии, ни digest-ом; один stage (для pure-python норм); HEALTHCHECK нет (HF пингует сам — приемлемо); версии зависимостей плавают (находка #3). `[data: 2025]`

**Workflows:** пять штук, зрелые. CI: ruff + pytest, кэш pip. Deploy: снапшот-пуш в Space с force (истории на Space нет — осознанно), LFS для бинарей, paths-ignore для data-коммитов (иначе каждый usage-коммит передеплоивал бы прод — учтено). Rescrape: расписание с учётом таймзоны и «бана по IP», ручные inputs с дефолтами, `--fail-empty`, job summary с JSON-статистикой, VACUUM перед выгрузкой. Retrain: снапшот старой модели → train → метрический гейт → Telegram-отчёт → коммит модели. Keepalive: пинг каждые 6 ч + ежедневный рестарт для подтяжки базы. Секреты — через GitHub Secrets, в логи не светятся (Actions маскирует). `[data: 2025]`

Замечания: `git pull --rebase` в retrain **после** коммита может конфликтовать с data-коммитами, прилетевшими за время обучения (~40 мин окно) — workflow тогда падает, модель теряется до следующего воскресенья; гонка рескрейп/рестарт (находка #14); зависимостного аудита (pip-audit/Dependabot) в CI нет — с плавающими версиями это двойной риск; отдельных окружений dev/staging нет — прод один, но для пет-проекта это норма.

## 6. Структурные проблемы (требуют осмысленного захода)

- **Состояние приложения в git-репозитории.** PII-риск (#1), неатомарные read-modify-write, потеря серверных записей при рестарте (#4), рост истории (#6) — это всё симптомы одного решения «git как БД». Оно осознанное и бесплатное, но у него есть срок годности: как только у бота появятся реальные подписчики, понадобится настоящее персистентное хранилище состояния (вариантов много — от приватного репо до бесплатных managed-SQLite; выбор за тобой). Это самый крупный архитектурный долг проекта.
- **Медленные внешние вызовы в потоке запроса (#2).** Систематическое решение — развести «быстрый ответ из модели/кэша» и «медленное обогащение» (очередь/фоновая задача/отдельный воркер), а не крутить sleep-ретраи в HTTP-хендлере. Частично паттерн уже есть (flags_pending + догрузка фронтом) — его стоит довести до конца и для скрейпинга.
- **Одноэкземплярная архитектура.** Rate limit, дедуп update_id, кэши, вебхук-статус — всё в памяти процесса; больше одного инстанса поднять нельзя. Пока трафик мал — не проблема; фиксирую как осознанное ограничение, которое стоит держать в голове при любом «давайте перенесём на другой хостинг».
- **Стратегия хранения ML-артефактов.** Еженедельные коммиты моделей в main (~15.5 МБ) уже дали 43 МБ `.git`. Механизм для больших файлов в проекте уже есть (GitHub Release для БД) — модели просятся туда же, вопрос только в том, как тогда деплоить Space (сейчас он берёт модели из снапшота репо).
- **Версионирование схемы SQLite.** Самодельный `_migrate` работает, но при следующем усложнении схемы (аренда! роадмап этапа 2) захочется явных версий схемы с историей и порядком применения.
