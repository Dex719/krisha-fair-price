## Оставшиеся риски

1. **GitHub как хранилище состояния.** Contents API не даёт атомарного read-modify-write между несколькими процессами; при росте трафика state следует перенести в приватную БД/объектное хранилище.
2. **Ограничение request body опирается на `Content-Length`.** Chunked-запрос без заголовка пока может обойти ранний 64-КБ лимит. Нужен ASGI streaming-limiter или лимит на доверенном reverse proxy.
3. **Rate limit локален одному процессу.** При горизонтальном масштабировании нужен общий Redis/proxy limiter. `TRUST_PROXY_HEADERS=1` безопасно включать только если приложение недоступно в обход доверенного прокси.
4. **Синхронные внешние вызовы в request thread.** Фото/Gemini/скрейпинг имеют таймауты, но под нагрузкой занимают thread pool; дальнейшая оптимизация — очередь или отдельный воркер.
5. **Контрольные суммы релизов опциональны.** При отсутствии `.sha256` база/модели принимаются без проверки; для production лучше сделать checksum обязательным.
6. **Предупреждение тестового стека.** FastAPI/Starlette сообщает о будущем переходе TestClient с `httpx` на `httpx2`; это не runtime-баг, но требует планового обновления тестов после стабилизации API.

## Настройка деплоя

Если сервис действительно стоит за единственным доверенным reverse proxy, добавьте `TRUST_PROXY_HEADERS=1`. Иначе переменную не задавать: безопасное значение по умолчанию — игнорировать пользовательский `X-Forwarded-For`.
