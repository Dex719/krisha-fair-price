## 1. Резюме

- **Объём аудита:** один Python-сервис (FastAPI + Telegram-бот + CatBoost ML + vanilla JS фронт), ~7 300 строк src/scripts + ~2 550 строк тестов (163 тест-функции в 30 файлах), SQLite, деплой на Hugging Face Spaces, батч-пайплайны в GitHub Actions.
- **Общее состояние:** это сильный пет-проект — по инженерной культуре выше многих продакшен-кодовых баз. Осознанные компромиссы задокументированы прямо в коде, ML-валидация честная, деградация всюду мягкая. Главные риски не в качестве кода, а в архитектурных ставках на «бесплатную» инфраструктуру: состояние в git, SQLite с перезаписью при рестарте, медленные внешние вызовы в потоках запросов — и один реальный прокол с приватностью (chat_id подписчиков в публичном репозитории).
- **Топ-3 сильных стороны:** честная ML-методология (group split, дедуп, CQR, метрический гейт); плотное тестовое покрытие с фикстурами реальной разметки; продуманная безопасность (SSRF-защита, webhook-секрет, CSP, экранирование XSS).
- **Топ-3 слабости:** PII (raw chat_id) уедет в публичный git при первом же подписчике; блокирующие внешние вызовы с ретраями до минут внутри HTTP-запросов; отсутствие lock-файла — невоспроизводимые сборки.
- **Самые серьёзные находки:** #1 chat_id в публичном репо (6/10), #2 threadpool-starvation через медленные ретраи (5/10), #3 плавающие версии зависимостей без лока (5/10).

## 2. Сильные стороны

**Честная ML-валидация — редкость даже в индустрии.** Сплит по «зданиям» через `GroupShuffleSplit` вместо случайного по строкам, дедупликация перевыставленных объявлений по отпечатку квартиры, ppsm-статистика и spatial-референс считаются только на train, early stopping по отдельному val (не по test), конформная калибровка интервала (CQR по Romano et al. 2019), а фичи, ухудшившие метрики на честном сплите, выключены с задокументированной абляцией (`EXTRA_FEATURES` в `features.py`). Еженедельный retrain защищён метрическим гейтом, который сравнивает старую и новую модель на одном и том же свежем test-сплите (`scripts/model_gate.py`) — это правильный способ не путать дрейф данных с деградацией модели. `[data: 2025]`

**Тесты.** 163 тест-функции на ~7 300 строк кода, включая парсеры на фикстурах с реальной разметкой krisha.kz, тесты БД, бота, API-схем и даже тест на security-заголовки (`tests/test_api_security.py`). `conftest.py` отключает скачивание базы в тестах. CI гоняет ruff + pytest на каждый push/PR.

**Комментарии, объясняющие «почему».** Почти каждое неочевидное решение снабжено причиной: почему WAL и busy_timeout (`db.py`), почему `local_address="0.0.0.0"` для Telegram на HF (`bot.py`), почему `time.monotonic()` нельзя инициализировать нулём (`bot.py`), почему выдача шардируется район×комнаты (`config.py`). Это резко снижает стоимость поддержки.

**Безопасность продумана для своего масштаба.** SSRF закрыт канонизацией URL по id (`predict.py`), Telegram-webhook защищён секретом с `hmac.compare_digest` и дедупликацией update_id, CSP + `X-Content-Type-Options` + `Referrer-Policy` навешаны middleware и проверяются тестом, фронт экранирует все данные с krisha.kz (`esc()`) и валидирует URL фото по whitelist-домену (`safePhoto()`), ошибки наружу отдаются обобщённо, детали — в лог. Хардкод-секретов в коде нет (проверено сканом). `[data: 2025]`

**Fail-soft деградация.** Без `TELEGRAM_BOT_TOKEN` — работает сайт; без `GEMINI_API_KEY` — работает оценка без LLM-бейджей; без базы — работает предикт по модели и `/api/stats` из снапшота; read-only ФС не роняет кэши. Паттерн выдержан последовательно по всей кодовой базе.

**CI/CD-контур полный:** lint+test → автодеплой на HF → ежедневный рескрейп с загрузкой БД в GitHub Release → еженедельный retrain с гейтом и Telegram-отчётом админу → keepalive-пинг с самолечением webhook. Concurrency-группы защищают от параллельных записей БД (`krisha-db-writes` общая у рескрейпа и retrain — правильно).

**Вежливый скрейпинг:** случайные задержки 2–4 с (в CI — 2.5–5), бэкофф на 403/429, единый User-Agent, resumable-обход, шардирование выдачи для честного покрытия. Дисклеймер о принадлежности данных в README.
