## ⚡ Как это работает

```mermaid
flowchart LR
    A["🔗 Ссылка<br/>на krisha.kz"] --> B["📄 Объявление<br/>~20 признаков"]
    B --> C["🧠 CatBoost<br/>цена + квантили"]
    C --> D["✅ Вердикт<br/>цена · диапазон · факторы"]
```

1. Вставляете ссылку на объявление о продаже или аренде квартиры в Алматы — на сайте или в боте (боту можно прислать и просто текст объявления о продаже).
2. Сервис загружает объявление и извлекает признаки: площадь, комнаты, этаж, возраст дома, район, ЖК, координаты, расстояние до центра…
3. Модель CatBoost считает справедливую рыночную цену и обычный диапазон, а затем сравнивает их с ценой в объявлении.
4. Ответ: вердикт, отклонение в процентах, диапазон цены и факторы с пояснениями. Рядом — похожие объявления, срок продажи и кнопка «Следить за ценой» в боте.

Для масштаба: наивный бейзлайн «медиана ₸/м² по району × комнатам» даёт MAPE ~16.5% — модель ошибается вдвое меньше. Покрытие интервала цены на тесте ~80% при цели 80%.

<details>
<summary><b>Под капотом</b> — признаки, интервалы, валидация</summary>

- Таргет `log1p(price)`, нативные категориальные признаки (район, микрорайон, ЖК, тип дома) — всего 47 фичей.
- Пространственные признаки: медиана ₸/м² по гексагонам H3 (res 7 и 8), для метрик считается только на train (без утечки теста), у прод-модели — на всех данных; снапшотится в `models/spatial_ref.json`.
- Интервал цены: MultiQuantile-модель (квантили 10%/90%) с конформной калибровкой (CQR).
- Объяснимость: SHAP-факторы на каждый прогноз + глобальный отчёт [`reports/shap_summary.png`](reports/shap_summary.png).
- Валидация: временно́й holdout (тест — объявления, впервые увиденные за последние 14 дней) с дедупом и purge перевыставлений. После оценки модель переобучается на всех данных, включая тест, — в прод уходит она (на walk-forward стенде −0.3 п.п. MAPE).

</details>

## 🤖 Telegram-бот и Mini App

Тот же сервис в Telegram — **[@fairprice_kzbot](https://t.me/fairprice_kzbot)**:

| Команда | Что делает |
|---|---|
| ссылка на объявление | оценка, как на сайте: справедливая цена, диапазон, факторы |
| текст объявления без ссылки | примерная оценка по описанию |
| `/track ссылка` | слежение за объявлением: напишу, если цена изменилась или объявление сняли |
| `/alerts_on 2к до 45млн бостандыкский` | раз в день — новые объявления дешевле оценки, с фильтрами по комнатам, бюджету и району |
| `/untrack`, `/alerts_off` | перестать следить и отписаться |

Mini App открывает полный интерфейс сайта, а сайт связан с ботом ссылками («Следить за ценой», подписка на район со страницы рынка). Бот живёт на том же FastAPI через webhook (`POST /tg/webhook`) — отдельный сервер не нужен. Для своего деплоя достаточно `TELEGRAM_BOT_TOKEN`: webhook регистрируется при старте, а проверка раз в час чинит его, если слетел.

## 🔁 Данные и надёжность

Конвейер целиком на GitHub Actions, без ручных шагов:

- **Ежедневный сбор** — свежие цены, новые объявления, отметки о снятии; вежливые задержки. Прогон **падает**, если собрал ноль или подозрительно мало (`--fail-empty`, `--fail-below`) — тихая деградация парсера исключена.
- **База и веса модели** хранятся в релизах приватного репозитория данных с контрольной суммой sha256; Space скачивает и проверяет их при старте. Код открыт, накопленные данные — нет.
- **Еженедельное переобучение с гейтом качества**: новая модель заезжает, только если не хуже старой на свежем тесте.
- **Деплой только после зелёного CI**, а смоук ждёт, пока прод поднимется именно на выкаченной ревизии (`/api/health` → `revision`).
- **Проверка каждые 6 часов**: живость, свежесть данных, webhook бота; при сбое — уведомление в Telegram.

<details>
<summary><b>Счётчик посещаемости и подтверждение прав</b> — переменные Space и события GA4</summary>

Счётчик посещаемости (Google Analytics 4) и коды подтверждения прав задаются переменными Space — в разметке их нет, и без переменных сайт работает без счётчика (CSP тогда без внешних адресов):

| Переменная | Что это |
|---|---|
| `GA4_MEASUREMENT_ID` | поток Google Analytics 4, `G-…` |

Свой счётчик визитов (`usage`, недельная сводка) из-за кэша страниц в воркере видит только промахи кэша — визиты смотреть в GA4.

## 🚀 Быстрый старт

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"   # dev включает train-extras (shap, matplotlib)

make crawl        # быстрая проба: ~50 объявлений в data/krisha.db
make crawl-full   # полный обход Алматы (часы — вежливые задержки)
make train        # обучение CatBoost → models/model.cbm + SHAP-отчёт
make api          # http://localhost:8000 — веб-интерфейс + API
make test         # pytest
```

Runtime-деплой (Docker/HF Spaces) ставит только `pip install -e .` — тяжёлые train-зависимости (`shap`, `matplotlib`, `scikit-learn`) вынесены в optional extra `train`: `pip install -e ".[train]"`.

`requirements*.lock` собраны под Linux (CI/Docker); локальная разработка на Windows/macOS — `pip install -e ".[dev]"`. Docker ставит из `requirements.lock`, чтобы prod и Actions не разъезжались на версиях. После правки зависимостей в `pyproject.toml` — `make lock` и закоммить оба лока в том же PR.

Сбор аренды — отдельная база `data/krisha_rent.db`, на ней учится модель аренды:

```bash
python scripts/rescrape.py --deal arenda --max-new 1000
```

<details>
<summary><b>Под нагрузкой</b> — расчётный сценарий: ссылку постят в большой телеграм-канал, тысяча человек за две минуты</summary>

- *Горячие ответы* живут в памяти процесса: `/api/health` — 60 с, `/api/stats` и `/api/heatmap` — 10 минут, готовый разбор объявления — 10 минут по id лота. Кэш с single-flight: пересчёт делает один поток, остальные ждут результат; если пересчёт упал — отдаётся последнее удачное значение вместо 503.
- *Статика отдаётся из памяти предсжатой* (`api/static_cache.py`): gzip считается один раз при старте — на локальном замере сжатие на лету стоило половины пропускной способности `/`. ETag от содержимого, `If-None-Match` → 304.
- *Тяжёлый предикт ходит через одну калитку* (`predict_gate.py`) — и веб, и бот: кэш по id лота, single-flight, негативный кэш на битые ссылки, лимит одновременных скрейпов, короткий сетевой бюджет (5 с вместо краулерных 30). Если все слоты заняты дольше `PREDICT_WAIT_S` — честные 503 + `Retry-After` вместо висящего спиннера.
- *Лимиты раздельные*: `/api/demo` не делит бюджет с `/api/predict` — за CGNAT мобильного оператора под одним IP сидит целый город.
- Приложение поднимается в `WEB_CONCURRENCY` процессов (по умолчанию 2). Замер — `python scripts/loadtest.py <url>`, живой прод — `/api/metrics`.

</details>

```
├── scraping/       # вежливый HTTP-клиент (задержки, ретраи), парсеры выдачи и деталей, resumable-краулер, рескрейп
├── features.py     # очистка + фичи (этажность, возраст дома, до центра, карты ₸/м²)
├── train.py        # обучение CatBoost, бейзлайн, честная валидация, SHAP
├── predict.py      # ссылка → вердикт
├── factor_hints.py # подсказки к факторам языком покупателя
├── market.py       # рыночная статистика: срез по районам, срок до снятия
├── bot.py          # Telegram-бот: webhook → predict → ответ; /track, /alerts, ссылки с сайта
├── api/            # FastAPI, отдача страниц, живые цифры в разметке, счётчик посещаемости
└── db.py           # SQLite: схема, upsert по id, история цен
static/             # фронт на дизайн-системе baǵam (design.css): оценка, рынок, бот, о проекте
infra/              # Cloudflare Workers: домен bagam.info и прокси Bot API
assets/             # логотипы и скриншоты для README
tests/              # ~970 тестов: парсеры (фикстуры с реальной разметкой), фичи, БД, бот, API, страницы, артефакты модели
tests/e2e/          # 96 e2e поверх настоящего uvicorn: браузерные (pytest-playwright) + контракт API и статики, из них 3 live-smoke
```

E2e-тесты не входят в `make test` (нужен Chromium): `playwright install chromium`, затем `make test-e2e`. Живой smoke с реальной базой и одним походом на krisha.kz — `pytest -m live` (только вручную).
